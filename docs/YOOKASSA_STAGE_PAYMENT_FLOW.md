# СтройВыбор: этапные расчёты через ЮKassa

## 1. Обязательный жизненный цикл проекта

1. Заказчик публикует проект.
2. Подрядчики отправляют предложения.
3. Заказчик принимает одно предложение и выбирает подрядчика.
4. Сервис предлагает заказчику сформировать договор.
5. Заказчик настраивает условия в конструкторе и создаёт версию договора.
6. Заказчик и подрядчик подписывают одну и ту же текущую версию.
7. Только после двух подписей открываются этапы работ и финансовые разделы.
8. Подрядчик формирует этапы и начинает первый этап. В этот момент проект становится `in_progress`.
9. Деньги конкретного этапа могут быть внесены/зарезервированы у платёжного провайдера, но подрядчику не выплачиваются.
10. Подрядчик завершает этап и отправляет его на приёмку (`awaiting_review`).
11. Заказчик либо возвращает этап на доработку (`revision_required`), либо принимает (`completed`).
12. Только переход этапа в `completed` переводит платёжное намерение в `release_ready`.
13. Backend создаёт payout в ЮKassa только для `release_ready`.
14. Webhook подтверждает фактическую выплату и переводит платёж в `paid`.
15. При споре автоматическая выплата блокируется до решения.

## 2. Почему обычный двухстадийный платёж не является эскроу для стройки

Стандартное `capture=false` в ЮKassa — предавторизация. Срок удержания ограничен способом оплаты и обычно значительно короче строительного этапа. Поэтому нельзя держать месячный этап обычным card hold.

Для длительного удержания нужно согласовать с ЮKassa подходящий marketplace-сценарий. В документации ЮKassa «Безопасная сделка» позволяет удерживать деньги до завершения сделки, но выплаты этого продукта имеют ограничения по типу получателя. Так как в СтройВыбор подрядчиками могут быть ИП и ООО, перед production-интеграцией необходимо получить у менеджера ЮKassa письменное подтверждение подходящей схемы для каждого типа исполнителя.

Если для ИП/ООО будет предложено «Сплитование платежей», необходимо отдельно подтвердить механизм отложенной выплаты: обычное сплитование распределяет платежи магазинам и само по себе не заменяет этапное удержание.

## 3. Состояния `project_payment_intents`

- `planned` — этап и сумма сформированы, оплаты ещё нет.
- `awaiting_payment` — заказчику выставлена оплата.
- `funded` — деньги успешно получены/зарезервированы в схеме провайдера.
- `stage_submitted` — подрядчик отправил этап на приёмку; деньги всё ещё заблокированы.
- `release_ready` — заказчик принял этап; приложение разрешило выплату.
- `payout_processing` — запрос выплаты отправлен провайдеру.
- `paid` — webhook провайдера подтвердил выплату подрядчику.
- `disputed` — есть спор; release запрещён.
- `refund_pending` — инициирован возврат.
- `refunded` — возврат подтверждён провайдером.
- `cancelled` — платёжное намерение отменено до расчёта.

## 4. Неизменяемые правила безопасности

- API/UI не должны иметь команду `pay contractor` для этапа со статусом, отличным от `completed`.
- Проверка выполняется и в приложении, и constraint/trigger-слоем PostgreSQL.
- Webhook ЮKassa никогда не считается подтверждением качества работ.
- Только решение заказчика по этапу создаёт `release_ready`.
- Подрядчик не может подтвердить этап за заказчика.
- Спор или admin risk hold блокирует payout.
- Все provider requests используют idempotency key.
- Все входящие webhook события сохраняются с provider event/payment/deal ID и обрабатываются идемпотентно.
- Сумма payout берётся из зафиксированного платёжного намерения/договора, а не из параметра браузера.
- Секретный ключ ЮKassa хранится только server-side.

## 5. Webhook flow

### Оплата заказчиком

`payment.succeeded` / соответствующее событие безопасной сделки:

- сверить provider payment ID;
- сверить сумму и валюту;
- связать с `project_payment_intents.id` из metadata;
- перевести `awaiting_payment -> funded`;
- уведомить стороны, что деньги зарезервированы;
- подрядчику деньги не отправлять.

### Приёмка этапа

`project_stages.awaiting_review -> completed`:

- PostgreSQL переводит `funded|stage_submitted -> release_ready`;
- worker берёт только `release_ready`;
- создаёт payout с idempotency key;
- `release_ready -> payout_processing`.

### Выплата

Webhook успешной выплаты:

- `payout_processing -> paid`;
- сохранить provider payout ID и время;
- уведомить заказчика и подрядчика.

Ошибка выплаты:

- не помечать как `paid`;
- оставить/вернуть в безопасное retry-состояние;
- записать код ошибки провайдера;
- уведомить администратора при превышении retry policy.

## 6. Что нужно получить от ЮKassa перед включением production платежей

1. Какой продукт применяется к заказчик -> ИП/ООО подрядчик с удержанием до приёмки этапа.
2. Можно ли одной сделкой обслуживать несколько этапных выплат либо нужна отдельная deal на этап.
3. Срок максимального хранения средств для выбранной схемы.
4. Модель комиссии СтройВыбора (`fee_moment`).
5. Поддерживаемые реквизиты payout для физлица, самозанятого, ИП и ООО.
6. Требования 54-ФЗ и кто формирует чек для заказчика и/или комиссии площадки.
7. Процедура возврата и блокировки денег при споре.
8. Требования к публичной оферте площадки и описанию безопасной сделки.

До получения этих ответов production-выплаты не включать. Бизнес-логика СтройВыбора при этом уже должна использовать provider-independent state machine выше.
